    Module 3 - Deploy a DataFlow Function

    1. Overview

    DataFlow Functions provides an efficient, cost optimized, scalable way to run NiFi flows in a completely serverless fashion for event-driven use cases. Some of these use cases are:

    • Serverless, Trigger-based File Processing
    • Serverless Web APIs
    • Serverless Microservices

    To accomplish this, you leverage the cloud providers serverless functions (AWS Lambda, Azure Functions or Google Cloud Functions. Each of these services provide different triggers to execute these functions (e.g. S3 trigger (when a file has landed in a bucket), HTTP trigger, etc. Each of these triggers sends a JSON payload to the function and is passed to the NiFi flow.

    As you will see in the Design Flow section, you will need to parse these payloads to extract the key/value pairs that will be used in the rest of the flow. Each cloud provider has a different payload/contract for these different triggers, so you will have to review the documentation for the trigger to see what the payload is and where the specific key/value pairs are for you to extract for your flow.

    For this module, you will be building out a flow that will process a file of syslog messages that are dropped into an S3 bucket and then published into a Kafka topic.

    2. Design Flow

    When writing a flow to be used in a DataFlow Function, you need to start with an input port. This port will receive the payload from the cloud function trigger (more about this process in section 3). If the cloud function requires the output from flow, then you will use an output port. For sending flow errors to the function, you will need another output port to route those failures to that will be captured by the cloud function. Beyond that, flow creation is the same.

    2.1. Create a new flow

    1. Create a new flow in flow designer with the pattern: USERNAME-syslog-kafka-dff
    2. Once the flow has been created, start a test session

    2.2. Define parameters for the flow

    Once the test session has started, you will need to define the controller services and parameters that will be used by the flow. For information about accessing and adding parameters, please refer to module 1.

    1. Go to Flow Options and select Parameters
    2. Add the following parameters:
    Parameter Name Description Default Value
    s3_region The s3 region that the bucket is located in us-east-2
    filter_rule The filter rule to limit flow files to be used. Select * From flowfile
    destination_bucket The name of the S3 bucket where the processed syslog records will be written to. dff-converted-files
    1. Add the following sensitive parameters (use Add Sensitive Parameter):
    Parameter Name Description Default Value
    aws_access_id The aws access id generated for the user that owns the S3 bucket <enter the provided AWS Access Key ID>
    aws_secret_key The aws access secret key generated for the user that owns the S3 bucket <enter the provided AWS Secret Access Key>
    1. Click on the Apply Changes button to save the parameters
    2. Click on the Back To Flow Designer link

    2.3 Define controller services for the flow

    For information on adding and searching for the different controller services, please refer to Module 1.

    1. Click on Flow Options > Services
    2. Add the Syslog5424Reader
      • Change the service name to SyslogReader_DFF
      • Apply the changes
      • Enable the service

    3. Add the JSONRecordSetWriter

      • Change the service name to SyslogJSONWriter_DFF

      • Change the following properties:

        Property Value
        Output Grouping One Line Per Object

      • Apply the changes

      • Enable the service

    1. Now return to the flow design

    2.4 Define the flow

    1. Drag a ProcessGroup onto the canvas and name it syslog_s3_kafka_dff and then enter the process group
    2. Now drag an Input Port onto the canvas and call it trigger-payload
    3. Drag another ProcessGroup to the canvas and name it payload-parser and enter that process group.
      1. Drag an Input Port onto the canvas name it payload
      2. Drag a processor onto the canvas and search for SplitJSON and set the following properties:
    Property Value
    JsonPath Expression $.Records
    • Self-terminate the failure and original routes
    • Apply the changes to the processor
      3. Drag a processor onto the canvas and search for EvaluateJsonPath. Change the following properties:
    Property Value
    Destination flowfile-attribute 
     Add the following properties to the processor:
    Property Value
    bucket $.s3.bucket.name
    key $.s3.object.key
    region $.awsRegion
    • Self-terminate the failure and unmatched routes
    • Apply the changes to the processor

    1. Drag an output port onto the canvas and name it S3TriggerParsed

    2. Now, let’s connect the dots:

      1. First, connect the input port, payload, to the SplitJSON processor.
      2. Connect the SplitJSON processor to the EvaluateJSONPath Processor with the split route.
      3. Lastly, connect the EvaluateJSONPath to the output port with the matched route.


    2. Click on the syslog_s3_kafka_dff link in the breadcrumbs, at the bottom of the Flow Designer screen, to go back to the parent process group.

    1. Now drag a processor onto the canvas and search for FetchS3Object and name it fetch_syslog_file. Set the following properties:
    Property Value
    Bucket ${bucket}
    Object Key ${key}
    Region Reference parameter > #{s3_region}
    Access Key ID Reference parameter > #{aws_access_id}
    Secret Access Key Reference parameter > #{aws_secret_key}
    • Self-terminate the failure route
    • Apply the changes to the processor.
    1. Drag a processor to the canvas and select a QueryRecord processor and name it filter_syslogs. Set the following properties:
    Property Value
    Record Reader SyslogReader_DFF
    Record Writer SyslogJSONWriter_DFF

    Now add a property that will add the filter rule to:

    Property Value
    filtered_syslogs #{filter_rule}
    • Self-terminate the failure and original routes
    • Apply the changes to the processor.
    1. Drag a processor to the canvas and select PutS3Object and name it write_syslog_json_file. Set the following properties:
    Property Value
    Object Key ${filename}
    Bucket #{destination_bucket}
    Access Key ID #{aws_access_id}
    Secret Access Key #{aws_secret_key}
    Region Reference parameter > #{s3_region}
    • Self-terminate the failure and success route
    • Apply the changes to the processor.

    1. Now, let's connect the dots…..
      1. Connect the input port, trigger-payload, to the process group, payload-parser
      2. Connect the process group, payload-parser, to the FetchS3Object, fetch_syslog_file
      3. Connect the success route from fetch_syslog_file to the QueryRecord processor, filter_syslogs
      4. Connect the filtered_syslogs route from filter_syslog to the PutS3Object processor, write_syslog_json_file

    2.5 Testing the flow

    Before we create the function in the cloud provider, we need to test the flow to make sure that the flow actually works. The cloud providers have documented the event payloads for all the triggers, so refer to their documentation and get the sample and update the payload to match what you are doing. The following are the steps to simulate a trigger event.

    1. In the Flow Designer, navigate to the root process group. You should just see the initial process group we created, called syslog_s3_kafka_dff.
    2. Drag a processor onto the canvas and select GenerateFlowFile processor.
    3. For this module, we are simulating a S3 Trigger Event, so update the Custom Text property of the GenerateFlowFile processor with the following JSON:
    {
  "Records": [
    {
      "eventVersion": "2.0",
      "eventSource": "aws:s3",
      "awsRegion": "us-east-2",
      "eventTime": "1970-01-01T00:00:00.000Z",
      "eventName": "ObjectCreated:Put",
      "userIdentity": {
        "principalId": "EXAMPLE"
      },
      "requestParameters": {
        "sourceIPAddress": "127.0.0.1"
      },
      "responseElements": {
        "x-amz-request-id": "EXAMPLE123456789",
        "x-amz-id-2": "EXAMPLE123/5678abcdefghijklambdaisawesome/mnopqrstuvwxyzABCDEFGH"
      },
      "s3": {
        "s3SchemaVersion": "1.0",
        "configurationId": "testConfigRule",
        "bucket": {
          "name": "example-bucket",
          "ownerIdentity": {
            "principalId": "EXAMPLE"
          },
          "arn": "arn:aws:s3:::example-bucket"
        },
        "object": {
          "key": "test%2Fkey",
          "size": 1024,
          "eTag": "0123456789abcdef0123456789abcdef",
          "sequencer": "0A1B2C3D4E5F678901"
        }
      }
    }
  ]
}
    1. Update the value of the following 2 elements in this JSON:
    2. name (under bucket) - Set this to the actual source bucket name that you created. E.g: dff-dko-bucket

    3. key (under object) - Set this to the actual directory you created under the source bucket. E.g data/syslog-records.txt

    4. Connect the GenerateFlowFile processor to the syslog_s3_kafka_dff process group

    5. Start all processors, except for the GenerateFlowFile
    6. Once all processors are running, select the GenerateFlowFile and select the ‘Run Once’ option.
    7. Inspect the flow and see if there are any errors/bulletins on any of the processors, examine the provenance and make sure everything looks okay and examine the data in the kafka topic you wrote to in SMM and make sure that it matches the data in the file.
    8. If everything passes, you can then stop all processors, then delete the GenerateFlowFile processor on the root process group.

    9. Now publish the flow into the catalog, giving it a unique name. Once it has been published, copy the CRN for the flow (that includes the version number as well). That will be needed for Step 3.

      Note: Make sure to copy the CRN associated to one of the versions of the flow. Not the global flow CRN.

    3. Running the flow as a serverless DataFlow Function

    3.1 Setting Up the Machine User

    Before moving out of CDP and into the cloud providers UI to configure the cloud function, you will need to create a machine user that will be used to pull the data flow from the catalog.

    1. First, navigate to the Management Console and select User Management

    1. Next, click on the Actions button and select Create Machine User

    1. Enter the machine user name. For the workshop, choose the pattern \<user_id>_aws_lambda_dff

    1. Once the user has been saved, search for the user and select it

    1. Next, click on the Actions button and select Generate Access Key:

    1. Once the key has been generated, make sure you copy both the Access Key ID and the Private Key.

    1. Next, click on the Actions button and select Update Roles

    1. You will be given a list of roles. Select DFFFunctionMachineUser and click on Update.

    1. Click on Environments, search for your environment and click on it. On the environment page, click on Actions > Synchronize Users.
    2. Go to the cloud provider's UI to begin setting up the cloud function and continue below.

    3.2 Setting up the Parameters

    For the workshop, we will be using the cloud provider’s UI. The documentation around DataFlow Functions also walks you through using the CLI for the cloud provider, giving the customer the ability to perform CI/CD for the functions.

    When deploying the DataFlow Function, you will have to manually create the parameters that you configured in the flow. While you can set the parameters as environment variables for the Lambda function, the recommendation is to use the cloud provider's secrets management tool, especially when dealing with credentials for databases and such. For this section, we will be leveraging AWS. Future versions of the documents will include Azure and GCP.

    1. First, search for the secrets manager for your cloud provider

    1. On AWS Secrets Manager, click on Store a new secret and select Other type of secret.

    1. In that screen, you can begin adding all the parameters as key/value pairs:

    1. Once you are done, click Next.
    2. Give it a name and description. If the customer wants to use CI/CD, they can provide an environment/app-type pattern, as seen below. For the workshop, follow the following pattern: <user name>/DFF/Syslog

    1. For the rest of the steps, accept the defaults. Review the changes and save the secret.

    1. One thing to take note of: the secret has a last retrieved date, so if something isn’t working with the function, look here first to make sure the secret is being accessed before digging into the logs.

    1. Once saved, go back into the secret and copy its ARN. You will need that to create the permissions for the Lambda service role to be able to access the secret.

    3.3 Setting up the Function

    1. Navigate to the search box and go to the Lambda function UI.

    1. Click on the region selector and ensure you are in the same region as the bucket that you're using.
    2. In this UI, select the Create function button

    1. In the Create function screen, select Author from scratch.
    2. Give the function a name, using the pattern <user_id>_syslog_dff.
    3. For Runtime, select the Java 8 on Amazon Linux 2.
    4. Click Create function to save.

    3. Also, increase the amount of Ephemeral storage to 4 GB (4096)

    4. Change the timeout to 3 minutes.

    3.4 Testing the Cloud Function

    1. Click on the Test tab of the AWS Lambda UI for your function

    1. Using the same JSON that you used in testing the FlowFile in Section 2.5, create a new event named test-event and click on Save.

    2. Click on Test to initiate the testing. This step may take a little bit, since it is starting from a ‘Cold Start’ and is allocating resources for the function. If the test is successful, you will get a success message. If there is an error, you will get an error box with a link to the error logs for that specific execution. Once you have several successful tests, you can then go to the next section to publish the function.

    3.5 Publish the Cloud Function

    Now that you have tested your function, time to publish it (which makes it active and responds to the trigger events.

    1. Click on the Actions button and click Publish new version

    1. A screen will come up, asking you to give an optional comment to the new version. Write a comment and select Publish. This will now make this version of the function active

    1. Click Add Trigger to connect a trigger to your function.

    2. Upload a file full of syslog messages to the S3 bucket and folder you set the S3 trigger to monitor and then you should then see your file in the destination bucket.s
